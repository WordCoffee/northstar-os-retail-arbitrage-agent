## The defect the live run found

A one-clause brief — "…matte kraft pouch…, no text or logos" — lost **its subject**:
`sanitize_brief_for_render` dropped the entire clause because it mentioned lettering, so the render
prompt was the suppression phrase alone. FLUX 3 answered with an unrelated object (a black wheel
hub). It looked like a product shot, which is worse than an error.

Fixed:
- negative lettering is stripped as a **phrase**, keeping the art direction, including `no text **or
  logos**` list tails;
- a **positive** demand ("must read …", "headline sized to read") still drops the whole clause,
  because the model would paint it;
- if nothing but the demand remains, `render_with_text_guard` raises `TextSafeBriefEmpty` and
  `POST /api/design-studio/generate` returns **422 `text_safe_brief_empty`** with a message telling the
  operator to describe the product, surface and light instead of rendering a plausible-looking wrong
  thing.

Three tests pin it (`tests/test_text_fidelity.py`): the subject survives, the positive demand still
drops, and an empty brief renders nothing at all.

## Limits, stated

- Text-to-image only on this endpoint (`models.edit: null`); the edit, cutout and upscale lanes are
  separate entry points with their own models.
- Rich (non `text_safe`) briefs **will** paint fake lettering — measured, `APBDE MUSOROM COFFEE`. Any
  listing or packaging render must use `text_safe` and put real copy on the vector layer afterwards.
- The GPU is shared: the local brain is unloaded first, and the render refuses with `vram_busy` rather
  than thrash.
- Local only. Nothing is sent to a provider and nothing is billed, so the hosted deployment cannot use
  this lane as it stands.
