## V9: dogfood four services through Ty's Vision

```
python -m tools.vision.dogfood --services design-studio,listings,socialpulse,competitor-monitor
passed 1 of 4
```

Each row: open the service in its own tab, screenshot it, read the page with the local vision
model (`qwen2.5vl:7b`, `describe_page`), then apply a checkable seller question — does the
page show the service's own vocabulary, and a number a seller could act on.

| service | opened | page read | seller task | evidence |
|---|---|---|---|---|
| **design-studio** | yes | "Design Studio — One studio for every creative asset your Amazon listings need", 27 controls (Canvas, Projects, Listing Images, A+ Brand Story, Storefront, Packaging & Mockups…) | **pass** | `dogfood_shots/design-studio.png` |
| **listings** | yes | "NorthstarOS — a web interface for interacting with a Northstar creative assistant" | **fail** — no listing vocabulary | `dogfood_shots/listings.png` |
| **socialpulse** | yes | same shell, same controls | **fail** | `dogfood_shots/socialpulse.png` |
| **competitor-monitor** | yes | shell or blank | **fail** | `dogfood_shots/competitor-monitor.png` |

**This is the finding that matters: three of the services that were "improved" today do not
render their own page.** `/ui/listings`, `/ui/socialpulse` and `/ui/competitor-monitor` open
the generic Bojo chat shell. `/ui/design-studio` and `/ui/beta` render correctly, so routing
works in general — the defect is specific to these routes.

Pixel evidence, not opinion: the screenshots differ from the home page by **7 and 9 cells out
of 2,560** for `listings` and `socialpulse`, against **1,971** for `design-studio` and
**2,110** for `beta`. They are the same page.

**Consequence for the scorecard:** `measured` currently credits a service whose route is
registered. That is not the same as a route that renders. Fixing this is now the top product
gap and it is queued.

## V3: ten-task parity through UIA

```
python -m tools.vision.parity --run --backend uia --base http://127.0.0.1:8101/ui/
backend uia, ran true, passed 5/10, recovery false
```

What works (5): opening a page, navigating, typing, the tab lifecycle, injection logging.
What fails (5): every task that needs to **read or locate page content** — `read_title`,
`find_nav`, `read_heading`, `count_elements`, `click_nav`.

The cause is structural and now measured: **Chrome 156 publishes no accessibility tree for
the renderer unless it was launched with `--force-renderer-accessibility`.** UIA returns ten
elements — window buttons and the tab strip — and nothing from the page. Ty launched this
instance without the flag, and the rule says Ty never kills Chrome, so the flag needs a
relaunch that belongs to the owner.

That makes the architecture explicit:

- **page content** → pixels: screenshot + local vision model (`describe_page`), which read
  Design Studio's title, purpose and 27 controls correctly, and only text leaves the machine;
- **window and tab management** → UIA, which is deterministic;
- **actions on the page** → coordinate clicks verified after the act.

V3 therefore does **not** pass, and it will not pass through UIA alone. Two ways forward, both
one line: relaunch Chrome with `--force-renderer-accessibility` (or with
`--remote-debugging-port=9222` for the CDP path). Until then, Chrome Connect stays the
controller and the quarantine gate stays refused.

## What the run changed in the code

Three real defects found by doing the thing instead of describing it:

1. **`_keys("enter")` typed the letters e-n-t-e-r** into the omnibox, because a bare string
   went to `pyautogui.hotkey` instead of `press`. Screenshot: `…/competitor-monitorenter`.
   Fixed, with three tests that forbid a single key from ever being expanded.
2. **Navigation was verified by title change**, which a single-page app never produces. Now
   verified by title change **or** a real pixel difference.
3. **`format: json` returns an empty response with images on this runner.** `describe_page`
   drops the decoder flag and lets the parser enforce the schema; `num_predict` raised to 700
   so the JSON is not truncated mid-object (the 400-token cap cut it off at 1,306 chars).
