## Why the backlog is not auto-dispatched (and what would change that)

A failing test is a real acceptance oracle. A node id is **not** a write scope: nothing in
`test_foo.py::test_bar` says which source file owns the defect, and guessing from a traceback is how
an autonomous loop edits the wrong file — or the test that grades it. So each proposal carries
`authorized: false` and `blocked: needs_author: name the write scope`, and `validate_task()` on a raw
proposal reports exactly the two things a human/author lane must add.

**To make that step autonomous** the author needs an *evaluator*, not more steps: candidate patches
scored against (a) the failing test, (b) the regression suite, (c) `agent_kernel/content.py`'s
semantic checks, and (d) a `steward/reviewer.py` verdict from a separate session, with best-of-N
selection. That is the next unit and it is the one that makes "creative with changes" safe.

## The capacity envelope (measured, and it is the real binding constraint)

| State | Free RAM | Readiness |
|---|---|---|
| FLUX 3 (ComfyUI) resident + `qwen3.5:4b` resident in Ollama | **2.9 GB** | **NO-GO** — `ram-floor`, `model-preload` (needs 6.0 GB) |
| after `ollama stop qwen3.5:4b` + stopping ComfyUI | **7.88 GB** | **GO, 0 failing checks** |

So on this 16 GB box the image lane and the code lane **cannot be resident together**. FLUX 3 stays
armed (`MEDIA_GEN_LIVE=1`) and starts on demand (`scripts/start-flux3.ps1`, ~1–2 min; the gateway
answers 503 until it is up — that is its documented contract). A campaign needs the inverse: release
the image lane and the resident model first. That handover is a scheduler task, not a bug.

Note: `qwen3.5:4b` runs **100% CPU** in Ollama (3.2 GB RAM, ctx 8192) — which is why a Ty task costs
minutes per step and why the 27B llama.cpp lane is the escalation target, not the default.
