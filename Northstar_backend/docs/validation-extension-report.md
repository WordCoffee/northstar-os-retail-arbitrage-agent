# Guarded 20-ASIN Validation Extension — Implementation Report

**STATUS: OFFLINE-VERIFIED AND LIVE-READY; NO LIVE PROVIDER RUN HAS BEEN AUTHORIZED OR EXECUTED.**

This report documents the additive, fail-closed validation extension for Northstar OS
Retail Arbitrage Agent. It extends (never replaces) the existing guarded proof-batch
architecture. Bright Data remains the primary validation source; DataForSEO is wired as
a secondary, default-disabled, standard-queue-only provider. Every gate fails closed and
no network request is created by any offline command.

---

## 1. Executive Summary

- A new module `validation_run.py` implements: a DataForSEO configuration boundary, a

  authorization record + gate, a durable JSONL budget ledger with idempotency, an offline
  planner, raw/normalized evidence storage, a provider comparison, and fail-closed

## 4. Storage Layout

Each run is isolated under `data/validation-runs/<run-id>/` (overridable via
`VALIDATION_RUNS_ROOT` for tests):

```
<run-id>/
  manifest.json
  authorization.json
  preflight-plan.json
  budget-ledger.jsonl
  raw/brightdata/<ASIN>.json
  raw/dataforseo/<ASIN>.json
  normalized/<provider>/<ASIN>.json
  comparisons/<ASIN>.json
  reports/plan-report.md
  logs/
```

The run directory is never overwritten by another run id; each id is isolated.

## 5. Run-Manifest Model

- Generated by `create_validation_manifest(run_id, source_path, environ)`.
- Reads the canonical 20-ASIN source from `VALIDATION_SOURCE_PREFLIGHT`
  (default `data/batch/proof-batch-preflight-20260818T060549Z.json`).
- Embeds `source_reference` = `{path, sha256, preflight_fingerprint, selected_count}`.
- Asserts exactly 20 ASINs (else `GuardError`); preserves each ASIN's `title_conflict`
  flag and marks the three manual-review ASINs (`B01H40O42I`, `B08R2SRN88`,
  `B00N54AJZE`) as `manual_review_only`.
- `status: planned`, `max_asins: 20`, `max_tasks_per_asin: 2`, `hard_cap_cents: 100`
  ($1.00), `mode: standard_queue`, `providers: [BRIGHTDATA, DATAFORSEO]`.
- `compute_manifest_fingerprint` binds run_id + sorted ASINs + caps + mode + providers.

## 6. Authorization Model

- `create_authorization(run_id, manifest, operator_confirmation)` requires
  `operator_confirmation == run_id` exactly, then re-validates mode, max_asins (20),
  provider set, and budget cap (≤ $1.00). Writes `authorization.json` with
  `manifest_fingerprint` + `preflight_fingerprint` + `config_schema_version`.
- `verify_authorization(run_id, manifest, ledger)` is the gate checked before any live
  submit/retrieve: it fails on missing record, run_id mismatch, manifest fingerprint
  mismatch, preflight fingerprint mismatch, provider mismatch, queue-mode mismatch,
  ASIN-count mismatch, or budget over cap.
- CLI: `authorize-check --run <id>` (read-only validity) and
  `authorize-check --run <id> --confirm <id>` (bootstrap record).
- Wrong/missing confirmation or record ⇒ blocked, never auto-approved.

## 7. Budget + Idempotency

- `Ledger` is a durable JSONL file with idempotency keys
  `sha256(provider|schema|run_id|asin|validation_type|mode|payload_fingerprint)`
  (no timestamp/UUID/secret).
- `ledger_add_planned` enforces `MAX_TASKS_PER_ASIN = 2` (raises `RunAbort`) and the
  `DEFAULT_HARD_CAP_CENTS = 100` ($1.00) ceiling. On overage it writes a
  `budget_rejected` entry (never submits) and raises `RunAbort`.
- `Ledger.add` dedupes by idempotency key (duplicate key ⇒ no second task).
- `total_reserved()` / `total_actual()` return integer cents; accounting is strictly
  integer-cent.

## 8. Planner + CLI

- `plan_run(run_id, manifest, cache_lookup=None)` classifies each ASIN as
  `manual_review_only` (3 ASINs), `retrieve_existing_task` (ledger has a remote task id),
  `cache_hit` (optional `cache_lookup`), `eligible_to_submit`, or `blocked`.
- Planner makes no network calls; it writes `preflight-plan.json` + a redacted
  `reports/plan-report.md` (no provider data, no secrets).
- CLI commands: `preflight`, `report-plan`, `authorize-check`, `execute-dataforseo`,
  `retrieve-dataforseo`, `report`. Live commands (`execute-dataforseo`,
  `retrieve-dataforseo`) verify every gate then refuse before any request is created.
- Offline commands verified to make zero network calls (see §14).

## 9. Evidence Model (raw / normalized / comparison)

- `store_raw` writes a wrapped payload `{provider, asin, stored_at, payload_hash, payload}`
  once; a second write with a different payload returns the existing path (immutable).
- `normalize_provider_record` returns `null` for any missing field and lists
  `data_gaps` / `coverage`. Never fabricates values.
- `compare_providers(brightdata_norm, dataforseo_norm, run_id)` returns
  `manual_review_required` for the 3 manual-review ASINs, `identity_match`,
  `identity_conflict` (title or pack-count mismatch), or `insufficient_source_coverage`.
  It never mutates its inputs and never overwrites the Bright Data record.

## 10. Provider Interfaces (confirmation)

- `DataForSEOTransport(ProviderAdapter)`: construction makes zero calls; `submit` /
  `retrieve` raise `GuardError` ("DataForSEO live transport is not enabled; no request
  created") because `DATAFORSEO_TRANSPORT_ENABLED = False`. `fetch` is
  `NotImplementedError` (reserved for future parity with `ProviderAdapter`).
- `BrightDataValidationInterface`: submit raises `GuardError` unless explicitly enabled;
  delegates to the existing `bright_data_client` only inside an authorized live call
  (never in this task).
- Credential access (`get_dataforseo_credentials`) is confined to the (disabled) live
  transport method and is never invoked by the planner/manifest/authorization.

## 17. Future Operator Live Sequence (not executed)

  unexercised and unverified against the real API in this task.
- `BrightDataValidationInterface.submit` is gated behind an explicit `allow_live` flag and
  is not invoked here.
- All economics/comparison outputs are research-only until a human authorizes a live run and
  confirms mappings; no purchase recommendation is generated automatically.
